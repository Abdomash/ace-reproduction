[code-00059] Summing Venmo transactions with a specific relationship group (e.g., roommates) for both sent and received directions in a date range:
```python
# After obtaining roommate_emails set from Phone app and venmo_access_token
import datetime
start_date = datetime.date.today().replace(month=3, day=1).isoformat()

def sum_amounts(transactions, role, roommate_emails):
    total = 0.0
    for txn in transactions:
        amount = txn.get('amount')
        if not isinstance(amount, (int, float)):
            continue
        if role == 'sent':
            counterpart_email = txn.get('receiver', {}).get('email', '').lower()
        else:
            counterpart_email = txn.get('sender', {}).get('email', '').lower()
        if counterpart_email in roommate_emails:
            total += float(amount)
    return total

sent_total = 0.0
page = 0
while True:
    sent_page = apis.venmo.show_transactions(access_token=venmo_access_token, direction='sent', min_created_at=start_date, page_index=page, page_limit=20)
    if not sent_page: break
    sent_total += sum_amounts(sent_page, 'sent', roommate_emails)
    page += 1

received_total = 0.0
page = 0
while True:
    recv_page = apis.venmo.show_transactions(access_token=venmo_access_token, direction='received', min_created_at=start_date, page_index=page, page_limit=20)
    if not recv_page: break
    received_total += sum_amounts(recv_page, 'received', roommate_emails)
    page += 1

total = round(sent_total + received_total, 2)
```

[cms-00009] When comparing numeric fields from API responses (e.g., play_count, like_count), always check if the field exists. If it is missing, either skip that record or assign a sentinel value (e.g., `float('inf')` for minimum, `-1` for maximum) to avoid false minima/maxima. Example: `play_count = details.get('play_count'); if play_count is None: continue`.
[cms-00010] When working with the album library, do not assume that `show_album_library` returns full song objects. It only returns `song_ids` (a list of integers). To get play counts or other song details, you must call `show_song` for each song ID individually. Failing to do so will result in missing data.
[cms-00013] When a task requires operating on the intersection of two data sources (e.g., 'songs in my playlists which I have liked'), always gather both datasets completely first, compute their intersection, and then operate only on the intersected set. Do not assume that one dataset (e.g., liked songs) already satisfies the constraint. For example, to rate liked songs that are in playlists: (1) paginate through show_playlist_library to get all playlists, (2) for each playlist call show_playlist to collect all song IDs, (3) paginate through show_liked_songs to get all liked songs, (4) filter liked songs to keep only those whose song_id is in the playlist song ID set, (5) then process the filtered set.
[cms-00014] When a task requires different actions based on membership in a precomputed set (e.g., liked songs), always use that set to gate the creation of new records. Separate the 'create if missing' path from the 'update if rating > 1' path. For example: (1) paginate through show_song_library to get all song IDs; (2) paginate through show_liked_songs to build a set of liked song IDs; (3) for each song in the library, check if a review exists; (4) if a review exists and its rating > 1, update it to 1; (5) if no review exists and the song is NOT in the liked set, create a 1-star review; (6) if no review exists and the song IS liked, do nothing. This ensures you only create reviews for unliked songs and only update existing reviews when necessary.
[cms-00015] When calling an API, pass only the parameters explicitly listed in its specification. Do not add extra parameters (e.g., access_token) even if they seem necessary based on other APIs. If authentication is needed, rely on the environment's implicit handling or include it only if the spec explicitly lists it.
